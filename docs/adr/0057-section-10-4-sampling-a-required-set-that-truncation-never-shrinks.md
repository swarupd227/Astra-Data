# ADR 0057 — §10.4 sampling: a required set truncation never shrinks

Status: accepted · 7 September 2026 · Story S7.5.1, opening F7.5

## Context

S7.5.1 opens F7.5 (Sampling and scale) — the backlog's own AC: *"As a parity engineer, I
want large result sets compared by stratified sample with the totals always compared in
full, so that proof completes on the biggest workbooks without losing the numbers that
matter."*

- Full compare up to `full_compare_max_rows`; above that, stratified by grain with the
  top-N rows by each measure's absolute value always included; sample size and seed
  recorded
- A sampled PASS is labelled SAMPLED on the verdict and on the G3 card

§10.4 itself, verbatim: *"Result sets up to full_compare_max_rows are compared in full.
Larger sets are compared on a stratified sample keyed by the grain (every distinct value
of the first grain dimension is represented) plus the top-N rows by each measure's
absolute value, so that the rows that matter most to a reader are always in the sample.
Sampling is recorded on the ParityCase and shown on the Parity Dashboard; a sampled PASS
is labelled as such."*

`SamplingRule` (`full_compare_max_rows`, `sample_rows`, `stratify_by`) has existed since
S7.1.1, declared and entirely inert — confirmed by direct research: no code anywhere read
any of its three fields before this story. `diff.py` (S7.4.1) always fully compared every
shared key.

## Decisions

### 1. Only the cell-comparison stage is ever sampled — key-set comparison and the row-count/totals check both stay on the full data

`diff_result_sets` already computes `missing_keys`/`extra_keys` as a plain set
difference over every key on both sides, and the row-count-and-totals check already
reads `expected.rows`/`candidate.rows` directly (S7.4.1's own "cheap early signal," ADR
0055 decision 6). Neither is touched by sampling — the AC's own "So that" clause is
implemented literally: *"proof completes on the biggest workbooks without losing the
numbers that matter."* Only the `for key in shared_keys: ...` cell loop trades every
key for a representative subset once `len(shared_keys) > full_compare_max_rows`.

### 2. Stratification defaults to the first grain dimension, per §10.4's own literal parenthetical — but `SamplingRule.stratify_by` is finally real

§10.4's own text names no configurable dimension at all; it describes exactly one
behaviour ("every distinct value of the first grain dimension is represented"). Rather
than leave `stratify_by` a ninth permanently-inert charter field once sampling itself
became real, `"grain"` (the charter's own default sentinel) resolves to exactly what
§10.4 describes, and any other value is looked up among the case's own grain columns —
stratifying by that column instead when found, falling back to the first dimension when
it names none of them (e.g. a measure name, which cannot meaningfully stratify a
categorical partition). Proven directly: `stratify_by="TradeDate"` (a real second grain
column) really changes which column is stratified on; `stratify_by="Margin"` (a measure,
naming none of the case's own grain columns) really falls back to the first dimension.

### 3. "The top-N rows by each measure's absolute value" needed an invented, disclosed number — `TOP_N_ROWS_PER_MEASURE = 20`

The identical "the spec names the existence of a bound but not its value" gap this
codebase has already filled several times (`DEFAULT_RETRY_TIMEOUT_MULTIPLIER`,
`MAX_FILTER_VALUES_PER_FILTER`). "Absolute value" is read per key as `max(|expected|,
|candidate|)` across whichever side actually carries a numeric value for that measure,
since either side could hold the more extreme number and a real discrepancy there is
exactly what a reader most wants caught — not only the expected side's own magnitude.

### 4. The required set (one key per stratum, plus every measure's own top-N) is never truncated to fit `sample_rows`

"Always included" is read literally: `sample_rows` is a target for the *additional*
random fill, not a hard cap the required rows compete against. When the required set
itself already exceeds `sample_rows` (a charter someone configured with an unusually
small budget relative to how many strata or measures there are), the final sample is
simply the required set — larger than `sample_rows`, and disclosed as such in
`diff.py`'s own docstring, rather than silently dropping a guaranteed representative or
a guaranteed outlier to hit a number. Proven directly: a `sample_rows` of 3 against 5
real strata still produces a sample larger than 3.

### 5. The seed is generated by the caller's own absence of one, not fixed — and always recorded on the result, never only on request

`diff_result_sets` gained one new optional parameter, `sampling_seed: int | None = None`.
Production callers (`verdicts.py`) never supply one, so a fresh seed is drawn per run via
`random.SystemRandom().getrandbits(63)` — real entropy, not a predictable counter. Either
way, whichever seed actually drove the sample is always returned on
`DiffResult.sampling.seed`, satisfying the AC's own "sample size and seed recorded"
literally rather than only when a caller happens to ask. Tests pass an explicit seed and
confirm the identical seed reproduces an identical sample bit for bit — the seed is real
evidence, not a decorative number.

### 6. "INCONCLUSIVE if... the sample could not be stratified" never fires under this algorithm — disclosed, not contrived

Stratification only needs a non-empty grain, and `diff_result_sets` already refuses (its
own pre-existing, separate INCONCLUSIVE) whenever the expected side has none, before
sampling is ever reached. There is no remaining way for this story's own stratification
step to fail once that guard has already passed — the identical "a spec-named cause is
declared but this codebase's own design never produces it" disclosure
`InconclusiveReason.SAMPLING_SHORTFALL` already carries for the adapter-level equivalent
(S7.3.2, ADR 0054), applied here to the diff-level cause with the same name in spirit.

### 7. Sampling is recorded on both `ParityCase` (§10.4's own literal instruction) and `Verdict` (the backlog's own AC, "on the verdict") — two real, disclosed `SpecDeviation`s

§10.4 says plainly "sampling is recorded on the ParityCase"; §14's own separate
relational-storage table sketch (a different section entirely) already names a single
`sampled` field at the case level, confirming the property belongs there even though
§4.1.1's own graph ontology table has never listed it. `ParityCase.sampled`/
`.sample_size`/`.sampling_seed`/`.sampling_strategy` are written on **every** diff, not
only a sampled one — a case's own record always reflects its *most recent* run, so a
later, unsampled re-run genuinely clears a previously-sampled case's own fields rather
than leaving a stale `True` behind (proven directly against real PostgreSQL + Apache
AGE). `Verdict.sampled` is a separate, disclosed addition: the backlog's own AC asks for
the label specifically "on the verdict," and the Parity Dashboard (S7.4.2) already reads
`Verdict`s directly for its per-run cases table — requiring a second query back to each
verdict's own `ParityCase` just to show a label would cost a real query for no real
benefit, since `ParityCase.sampled` remains the single source of truth this property is
denormalised from.

### 8. "On the G3 card" cannot be built by this story — the real fact is written now, the screen arrives later

Confirmed by direct research: G3 itself is F9.1/S9.1.1's own later, entirely unbuilt
scope — no G3 card exists anywhere in this codebase today, and no story before S9.1.1
can build one. `Verdict.sampled` is the real fact that card will read from once it
exists, the same "write the real fact now, the screen arrives later" posture this
codebase has already taken repeatedly (e.g. `ExceptionCase.screenshot_ref`). Extended
instead where a real, already-built consumer exists today: the Parity Dashboard's own
"Parity Run" cases table (S7.4.2) now shows a SAMPLED pill next to a PASS result whose
`Verdict.sampled` is true — the identical spirit of the AC's own ask, on the one real
screen currently able to show it.

## Consequences

- `diff.py`: `SamplingInfo` (`sample_size`, `total_keys`, `seed`, `strategy`,
  `stratified_by`), `TOP_N_ROWS_PER_MEASURE = 20`, `_resolve_stratify_column`,
  `_select_sample` (pure); `DiffResult.sampling: SamplingInfo | None`; `diff_result_sets`
  gains `sampling_seed: int | None = None`.
- `verdicts.py`: every diff now writes `ParityCase.sampled`/`.sample_size`/
  `.sampling_seed`/`.sampling_strategy` via `writer.set_node_properties` and
  `Verdict.sampled` alongside `result`/`failing_cells`.
- Ontology: `ParityCase` gains `sampled`/`sample_size`/`sampling_seed`/
  `sampling_strategy`; `Verdict` gains `sampled` — all additive, `SCHEMA_VERSION` bumped
  27 → 28, no migration file needed (matches the established additive-change precedent).
  Two new declared `SpecDeviation`s.
- Console: `api.ts`'s `VerdictRow`/`RunParityResult` gain `sampled: boolean`;
  `ParityDashboard.tsx`'s Parity Run cases table shows a SAMPLED pill next to a sampled
  PASS.
- New `tests/test_sampling.py` (11 pure unit tests: threshold behaviour, stratum
  coverage, top-N-by-measure inclusion even with a zero random-fill budget,
  `stratify_by` resolving to a real named column versus falling back, totals/row-count/
  key-set staying full under heavy sampling, seed reproducibility, seed generation).
  `diff_fixtures.py`'s own six-case sampling category corrected (no longer claims §10.4
  is unbuilt; each case's own PASS/FAIL is now explained by why sampling either
  triggered-and-degenerated or never crossed the threshold).
- New `tests/test_integration_sampling.py` (5 tests against real PostgreSQL + Apache
  AGE): a forced sample really writes `ParityCase`'s four properties and `Verdict.
  sampled`; the evidence bundle really carries the same facts; a later, unsampled run
  really clears a previously-sampled case; `GET .../parity-run` really surfaces
  `sampled` over HTTP.
- Verified: full graph-svc suite green alongside the new tests (only the one already-
  known `test_integration_g2_reminders.py` flake, unrelated); full console-web suite
  green (13 new/updated Parity Dashboard tests, including two proving the SAMPLED
  label's own presence and absence); `ruff`/`mypy`/`tsc`/`eslint` all clean;
  `ontology_check.py --spec`/`--generated` and `migration_check.py` all pass, correctly
  reporting five new additive properties and zero migration required.

## Alternatives considered

**Sample the key-set comparison and the row-count/totals check too, for a uniform "one
sampling mechanism everywhere."** Rejected — see decision 1. The AC's own "So that"
clause is explicit that totals must stay full; key-set comparison is already a cheap set
operation with no scaling problem sampling would solve, so sampling it would only
introduce a real risk (a missing key hidden by chance) for no real benefit.

**Leave `SamplingRule.stratify_by` permanently inert, matching its pre-story state, and
stratify unconditionally on the first grain dimension.** Rejected — see decision 2. Now
that sampling is real, leaving a charter field with no effect at all would be a
deliberate dead field in a document every other block of which is fully consumed;
resolving it to a real column when it names one costs little and closes a real gap.

**Truncate the required set down to `sample_rows` when it is larger, keeping a hard
cap.** Rejected — see decision 4. "Always included" is the AC's own literal word;
silently dropping a guaranteed stratum representative or a guaranteed top-N outlier to
respect a budget would contradict the one guarantee §10.4 exists to make.

**Use a fixed or caller-supplied-only seed, with no auto-generation.** Rejected — see
decision 5. A fixed seed would make every sample of an unchanged, large result set
identical forever, defeating the purpose of a *representative* sample across repeated
proof runs; requiring a caller to always supply one would push a concern (real entropy)
onto every call site instead of the one place — this module — that actually needs to own
it.

**Build a G3 card stub now, ahead of F9.1/S9.1.1.** Rejected — see decision 8. No G3
gate object, MU page, or acceptance workflow exists anywhere in this codebase to host
one; a stub card here would either duplicate S9.1.1's own future work or ship a shell
with nothing real behind it, the same reasoning this codebase has already applied to
every other forward reference it has disclosed rather than pre-built.

## Open questions for the product owner

- Should `SamplingRule` gain its own `top_n_per_measure` field, now that a real number
  (`TOP_N_ROWS_PER_MEASURE = 20`) governs real behaviour, the same way `RowRule.
  max_failing_cells` moved from a module constant onto the charter once the diff
  algorithm itself needed one (S7.4.1)?
- Now that `ParityCase.sampling_strategy` records a real, single strategy string
  (`"stratified_by_grain_plus_top_n_by_measure"`), is a second strategy ever expected —
  and if so, should the charter itself choose between them, or is this the only
  stratification approach §10.4 anticipates?
- Should the Parity Dashboard's own per-sheet aggregation (S7.4.2) also roll up a
  sampled-case count, alongside pass/fail/inconclusive, now that individual verdicts
  carry the fact — or does the per-run cases table's own SAMPLED pill already answer
  what a report owner needs without a further sheet-level rollup?
