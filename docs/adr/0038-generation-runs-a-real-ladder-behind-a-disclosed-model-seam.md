# ADR 0038 — Generation runs a real ladder behind a disclosed model seam

Status: accepted · 4 September 2026 · Story S5.3.1 (F5.3, opening it)

## Context

S5.3.1 opens F5.3, right after F5.2 (rules engine, ADR 0036/0037) closed: *"As a parity
engineer, I want C3 calculations generated by a model with the context contract and
validated up the ladder before proof, so that a model output can never reach the client
repository without passing execution. GenerationRequest (§9.4) carries: calc AST,
dependency closure, target table columns, matching patterns, charter excerpt, output
schema; the model returns a typed candidate (DAX or M, plus a one-line rationale). Ladder:
schema (typed JSON), parse (DAX parser), compile (deploy to dev model or EVALUATE syntax
check), proof (parity cases), human (only on escalation). Mode recorded as
GENERATED_PROVED; provenance carries gateway request id, provider, model, prompt hash,
context hash, temperature 0, token counts. Up to two regeneration attempts on parse or
compile failure with the error fed back; then the field is routed to the Exception Desk
with all attempts attached."*

Unlike every story F5.1/F5.2 shipped, S5.3.1 depends on infrastructure that is not a single,
already-precedented gap: no Model Gateway (§5.5, S5.3.2's own explicit scope) has ever called
an external model from this codebase; no DAX parser exists; no live Fabric dev workspace
exists to compile against (E11); no Arbiter/Proof Engine exists to grant a real parity
verdict (E7); `ExceptionCase` (§11.3) is declared but has never been written by any story;
and the regeneration-with-fed-back-error mechanism has no prior art anywhere in this
codebase. Given the number and shape of these gaps, the scoping decision was put to the
product owner directly (via a structured question, not assumed): build the full pipeline —
`GenerationRequest`, the ladder, the regeneration loop, real `Measure`/`ExceptionCase`/
`ProvenanceRecord` writes — end to end and tested, calling the model through a narrow,
disclosed fixture seam rather than either building a fake gateway or leaving the story
unbuilt pending S5.3.2. That is the decision this ADR records the reasoning for.

## Decisions

### 1. `ModelCaller`, not "the Model Gateway" — a narrower, disclosed seam S5.3.2 fills in

§5.5's own Model Gateway is provider-agnostic routing, eval-set-gated tenant policy,
budgets, and caching — S5.3.2's explicit, separate acceptance criteria ("Transpiler calls
`gateway.generate(...)` and never names a provider"). Building even a stub of that here
would mean redoing the same work twice under two different stories, or worse, freezing an
interface S5.3.2 has not yet designed. `generation.py` instead defines the narrowest thing
the ladder actually needs — a `Protocol` (`ModelCaller.generate(request, *,
previous_error)`) and a wired-in default (`FixtureModelCaller`) that never fabricates a
plausible-but-fake DAX candidate: every call is honestly declined with `NOT_EXPRESSIBLE`,
the identical discipline `FixtureTargetAdapter.smoke_query` (S4.3.1) already set for a
capability this platform cannot yet provide for real. S5.3.2 supplies a second `ModelCaller`
implementation against a real provider; the ladder, the regeneration loop, and every write
path are already real and already tested against that exact seam.

### 2. Rungs 1 and 2 are real; rungs 3 and 4 are disclosed, unconditional passes

§16.1's schema rung is pydantic (`ModelResponseSchema`, `extra="forbid"`) validating the
model's own response against §9.4's literal `output_schema` — a real, working check, no
infrastructure gap involved. The parse rung reuses `rules.dax_sanity_check` unchanged
(S5.2.1's own structural stand-in: balanced delimiters plus a known-function allowlist, not
a real grammar — a new DAX parser is its own S2.3.1-scale effort, not this story's). Compile
("deploy to dev model or EVALUATE syntax check") and proof ("parity cases") cannot be
verified at all today — no live Fabric dev workspace exists (E11) and no Arbiter exists to
grant a real parity verdict (E7) — so both rungs are unconditional, disclosed passes, the
identical posture `FixtureTargetAdapter.smoke_query` and `model_lifecycle.regression_status`
(S4.3.1/S4.3.3) already set for a capability nothing here can exercise for real. The
consequence, stated plainly rather than hidden: only rungs 1 and 2 can actually drive a
regeneration or an escalation today. That is the honest current shape of "validated up the
ladder," not a weaker version of it dressed up to look complete.

### 3. The regeneration budget is one shared pool of two, not two per rung

§16.1's own table implies "one regeneration" per failing rung (parse, separately, compile).
The backlog's own S5.3.1 wording is more specific and says something narrower: "up to two
regeneration attempts on parse or compile failure" — one shared budget covering both. Since
compile can never itself fail today (decision 2), the difference is presently moot in
practice, but the code follows the backlog's own more specific wording (`MAX_ATTEMPTS = 3`:
one initial attempt plus two regenerations total) per this epic's own established
precedent that the backlog wins when it is more specific than the spec's own general table.

### 4. `GenerationRequest` is assembled directly from the graph, the same footing `classify.py`/`rules.py` already established

The formal `TRANSPILER_CALC` context contract (`context/transpiler.py`) has no
`sheet_ctx`-shaped section, and extending it would mean touching `contract_check.py`'s own
CI guard and the GraphQL fragment machinery behind it — a second story's worth of change to
a system this one does not need. `build_generation_request` instead queries the graph
directly for every fact §9.4 names: the dependency closure (a bounded `DEPENDS_ON` walk,
`MAX_CLOSURE_DEPTH = 5`), the encoding worksheet's own shelf/filter/sort data, and matching
`Pattern`s (honestly empty today — no `Pattern` node has ever been written, F5.5 not built).
Two more gaps are real and disclosed rather than silently omitted: `model_ctx.tables`/
`.columns` are empty because no `Field→ModelTable` `MAPS_TO` edge has ever been written by
any story, including the Modeller's own S4.1.1 output; `charter_excerpt` is empty because no
G1 Tolerance Charter has ever been recorded anywhere in this codebase. Both carry an
explanatory `note` in the request document itself, not a silently-empty field a reader could
mistake for "nothing here."

### 5. `ExceptionCase.class` uses `UNKNOWN` — a real, disclosed taxonomy mismatch, not a false fit

§11.3's `ExceptionCase` is declared in the ontology but had never been written by any prior
story — this is the first to drive it, the same "declared since S1.1.1, driven for the first
time" trajectory `SemanticModel.state`/`Measure`/`Pattern` have each already taken.
`_FAILURE_CLASSES` (§11.1: `FILTER_CONTEXT`, `NULL_HANDLING`, `DATE_GRAIN`, ...) is a
taxonomy for *parity* failures the Mender diagnoses after a real proof attempt — a different
moment from this story's own pre-proof generation failures (a schema rejection, a
`NOT_EXPRESSIBLE` decline, or an exhausted parse budget). Forcing one of those categories
onto a generation-time escalation would misclassify it under a label that does not describe
what happened. `class="UNKNOWN"` is used instead, with the mismatch disclosed directly in
`_write_exception_case`'s own docstring rather than left for a reader to discover later.

## Consequences

- New module `generation.py`: `GenerationRequest`/`build_generation_request`,
  `ModelResponseSchema`, `ModelCaller`/`FixtureModelCaller`, `LadderAttempt`/`_run_ladder`,
  `GenerationOutcome`/`generate_c3_field`, `GenerationEngine`.
- `ProvenanceRecord` gains `provider`/`gateway_request_id`/`temperature` (migration v0020,
  additive, no ontology change — a platform-table column addition, §21's own table, not an
  estate-graph node).
- New routes: `GET /v1/calculations/{calc_id}:generation-request` (any Artizent role),
  `POST /v1/calculations/{calc_id}:generate` (parity engineer).
- A successful generation writes a real `Measure` (mode `GENERATED_PROVED`, class `C3`), a
  `MAPS_TO` edge, and a `ProvenanceRecord` carrying the full §4.2 `model_call` block. An
  exhausted, declined, or schema-rejected generation writes a real `ExceptionCase`.
- No `pattern_ref` on a `GENERATED_PROVED` `Measure` or its `MAPS_TO` edge: a generated
  candidate was not produced by a rule or a `Pattern`, so the property is omitted rather than
  written as an explicit null — the same convention `rules.py`'s own C1/C2 writes follow.
- No console changes — S5.3.1's own acceptance criteria names no screen; an Exception Desk
  screen (reading the `ExceptionCase`s this story now writes) is F5.4/F11's own territory.
- Every write path is real Postgres/AGE, tested against real graph data
  (`test_integration_generation.py`); the ladder and regeneration logic are tested as pure
  functions against a scripted `ModelCaller` test double, since `FixtureModelCaller`'s own
  always-`NOT_EXPRESSIBLE` behaviour would never exercise a parse failure, a successful
  regeneration, or an exhausted attempt budget (`test_generation.py`).

## Alternatives considered

**Defer S5.3.1 entirely until S5.3.2 ships the real Model Gateway.** Rejected — the product
owner's own explicit choice (via `AskUserQuestion`) was to build the full pipeline now behind
a disclosed seam, not to block an entire feature on a sibling story's own infrastructure. The
ladder, the regeneration loop, and the write paths are real and independently valuable today;
S5.3.2 only has to supply a second `ModelCaller`, not rebuild the pipeline around one.

**Build a stub "Model Gateway" (provider routing, budgets, caching) as part of this story.**
Rejected — see decision 1. That is S5.3.2's own explicit, separate scope; building it here
would either duplicate that story's work or freeze an interface it has not yet designed.

**Claim rungs 3/4 pass by writing a fabricated "compiled successfully" / "proof passed"
detail with no real check behind it.** Rejected — see decision 2. This module never
fabricates a check that doesn't verify what it claims, the same discipline ADR 0036/0037
already applied twice in this epic. The disclosed-pass posture states plainly what nothing
here can verify yet, rather than dressing up an unconditional pass as a real one.

**Extend the formal `TRANSPILER_CALC` context contract with a `sheet_ctx`-shaped section.**
Rejected — see decision 4. `classify.py`/`rules.py` already established the precedent of
querying the graph directly for facts a formal contract doesn't carry; extending the contract
machinery (and its own CI guard) for one story's own request shape is disproportionate to
what this story needs.

**Force a best-fit `_FAILURE_CLASSES` category (e.g. `UNKNOWN`'s nearest neighbour) onto a
generation-time escalation instead of using `UNKNOWN`.** Rejected — see decision 5. Any of
the named categories describes a *parity* diagnosis this story's own escalations are not;
picking one that merely sounds plausible would be a false categorization, not an honest gap.
